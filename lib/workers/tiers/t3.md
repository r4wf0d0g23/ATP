# Worker Tier 3 — Deep Validator

## Identity
- **Competency:** Deep validation, PR quality review, report cleansing, cross-run synthesis
- **Trigger:** PR opened or updated in ATP repo; also scheduled for report cleansing
- **Model class:** `capable` (highest reasoning quality — cost decreases over time)
- **Session type:** Persistent named session (`session:atp-t3-validator`)
- **Authorization:** Read all, comment on PRs, approve PRs, cleanse reports, update var metadata

## Responsibility

T3 is the quality gate. It reasons deeply about PRs before they merge, runs actual `verify_cmd` validation, and cleanses the reports directory into a coherent, deduplicated, actionable audit trail.

## Cost-Frequency Scaling

T3 runs at a frequency governed by the `cost_efficiency_ratio` variable:

```
T3_schedule = base_schedule × (1 / cost_efficiency_ratio)
```

| cost_efficiency_ratio | Base schedule | Effective schedule |
|---|---|---|
| 1.0 | Weekly | Weekly |
| 0.5 | Weekly | 2× weekly |
| 0.25 | Weekly | 4× weekly (near-daily) |
| 0.1 | Weekly | Daily |
| 0.05 | Weekly | 2× daily |

The `cost_efficiency_ratio` is read from `atp-instance/vars/worker-config.md` at job creation time. The cron schedule is recalculated when this var is updated.

## Execution Sequence

### PR Validation Mode (triggered by PR event)

```
1. LOAD PR CONTEXT
   Read PR: title, description, diff, changed files, T1/T2 findings (from PR comments).
   Load session history: has T3 seen similar patterns in past PRs?

2. DEEP SCHEMA VALIDATION
   For each changed file in the PR:
   a. Full schema conformance check (not just required fields — validate value quality)
   b. semantic_summary quality check: is it distinctive? does it add embedding density?
      Would it retrieve correctly vs. similar protocols? If weak → request changes.
   c. preload_size_class accuracy: does the estimate match the declared requires?
   d. guardrails completeness: are there obvious failure modes not covered?
   e. escalation coverage: does every critical path have an escalation rule?

3. VERIFY_CMD VALIDATION (for var file PRs)
   Run each modified var's verify_cmd (if safe to execute in current context).
   Apply the declared validator type.
   Record validation-result.
   If pass → note in PR comment.
   If fail → block PR with explanation.

4. CROSS-PR PATTERN DETECTION
   Using persistent session history:
   Has this type of finding appeared in multiple PRs?
   If yes → surface pattern to deployment owner as a systemic issue,
   not just a one-off finding.

5. PR DECISION
   a. APPROVE: all checks pass, quality is sufficient for merge
   b. REQUEST CHANGES: specific issues found, detailed feedback provided
   c. BLOCK (critical): critical finding — escalate before any merge

6. WRITE PR COMMENT
   Structured comment format:
   - T3 Validation Summary (pass/changes-requested/blocked)
   - Findings list (if any)
   - Verify_cmd results (if applicable)
   - Pattern notes (if cross-PR pattern detected)
   - Approval signal (if clean)

7. CAPTURE TRAINING PAIRS (metacognitive feedback loop)
   For every correction T3 made during this validation run — every REQUEST CHANGES,
   every BLOCK, every override of a T1/T2 verdict, every weak `semantic_summary`
   rewrite suggestion, every escalation reasoning chain — emit a training pair to
   `atp-instance/corrections/YYYY-MM-DD-t3-pr<N>-<slug>.jsonl`.

   Each line is one JSON object conforming to the training-pair schema:
   {
     "pair_id": "<uuid-v4>",
     "timestamp_utc": "<ISO-8601>",
     "source": "t3-validation",
     "pr_number": <N>,
     "finding_origin": "t1" | "t2" | "t3-self" | "none",
     "input": {
       "prompt_context": "<the situation T3 was reasoning about — file diff, prior worker finding, schema state, whatever was in T3's working set>",
       "prior_verdict": "<what T1/T2 said, or null if T3-originated>",
       "file_path": "<target file>",
       "file_excerpt_before": "<relevant slice — bounded to 200 lines>"
     },
     "output": {
       "t3_verdict": "approve" | "request-changes" | "block" | "override",
       "t3_reasoning": "<full chain — why T3 disagreed/agreed/escalated>",
       "t3_correction": "<the actual fix or recommendation>",
       "file_excerpt_after": "<post-correction slice if applicable, else null>"
     },
     "finding_type": "<schema/private-leak/semantic-quality/etc>",
     "confidence": "high" | "medium" | "low",
     "human_validated": false
   }

   Rules:
   - One pair per discrete correction. Do NOT bundle multiple findings into one pair.
   - PRIVACY GATE: before writing, run the same private_content scrubber that T2 uses
     against `prompt_context`, `file_excerpt_before`, `file_excerpt_after`, `t3_reasoning`,
     and `t3_correction`. Replace absolute paths, IPs, Tailscale hostnames, ssh literals
     with placeholders. If scrubber cannot fully sanitize → SKIP the pair, write a
     `corrections/skipped-YYYY-MM-DD.jsonl` audit line with reason. Never emit raw
     deployment-specific content into the corpus.
   - The `corrections/` directory is the training corpus. T3-cleanse never deletes it.
     A future fine-tune job consumes it; corpus retention is unbounded by design.
   - When `human_validated: false`, the pair is provisional — only flips to `true` when
     a human merges the corresponding PR (or explicitly approves T3's reasoning). The
     PR-merge webhook is responsible for the flip.
   - If a PR is later REJECTED or REVERTED by a human, mark all pairs from that PR with
     `human_validated: false` and add `negative_signal: true`. Negatives are training
     data too — they teach the future model what NOT to do.
```

### Report Cleanse Mode (scheduled)

```
1. LOAD ALL REPORTS
   Read all files in atp-instance/reports/.
   Parse each as worker-report.

2. DEDUPLICATION
   Find reports with identical findings (same file, same type, same description).
   Keep the most recent; remove older duplicates.
   Record dedup count.

3. STALE REMOVAL
   Reports older than 90 days with status=clean → archive to atp-instance/reports/archive/
   Reports older than 180 days → delete.
   Reports with all findings resolved → mark as resolved, archive.

4. ANOMALY SYNTHESIS
   Identify recurring finding types across reports.
   If same finding appears in ≥3 reports over ≥2 weeks → synthesize into a
   systemic-anomaly record (new finding type: cross-report pattern).
   This surfaces patterns that individual T1/T2 runs see in isolation.

5. WRITE CLEANSE REPORT
   atp-instance/reports/YYYY-MM-DD-t3-cleanse.json
   Include: duplicates_removed, stale_removed, anomalies_synthesized, patterns_detected

6. ANNOUNCE
   Send cleanse summary to ops-console.

7. CORRECTIONS CORPUS HEALTH CHECK
   Independent of report cleansing, audit `atp-instance/corrections/`:
   - Count total pairs, pairs by `finding_origin`, pairs by `human_validated` state
   - Flag if any pair predates schema version currently in use (mark `schema_version_stale: true`
     but do not delete — stale-schema pairs are still useful negative signal)
   - Surface in cleanse report: `corrections_corpus: { total_pairs, validated_pairs, by_origin, by_finding_type }`
   The corpus itself is NEVER pruned, archived, or deleted by cleanse — it is permanent training data.
```

## Metacognitive Feedback Loop → Future Training Corpus

T3 acts as the senior reviewer over T1/T2 output and over its own prior decisions.
Every correction T3 makes is a free, high-quality training signal: a `(situation, prior_verdict, T3_correction, T3_reasoning)` quadruple where the correction has been (or will be) human-validated via the PR merge gate.

This directive captures those quadruples as a JSONL training corpus at `atp-instance/corrections/`, suitable for:
- LoRA / SFT fine-tuning of a smaller model to replicate T3's review behavior at lower cost (the `cost_efficiency_ratio` lever from worker SPEC §Cost-Frequency Scaling Law)
- DPO/preference training using `(prior_verdict, T3_correction, human_validated)` triples
- Distillation into a future T2.5 tier that can absorb routine corrections without escalation

The corpus is the durable artifact of the metacognitive loop — without it, T3's reasoning is spent the moment a PR merges.

**Privacy boundary is non-negotiable:** the corpus may eventually leave the deployment for training infrastructure, so the same private_content scrubber that gates PR comments gates corrections capture. If the scrubber cannot guarantee sanitization, the pair is dropped with an audit line, never partially emitted.

## Cron Configuration (template — frequency governed by cost_efficiency_ratio)

```bash
# Base schedule: weekly. Recalculate when cost_efficiency_ratio changes.
openclaw cron add \
  --name "atp-t3-validator" \
  --cron "0 3 * * 0" \
  --tz "UTC" \
  --session session:atp-t3-validator \
  --model capable \
  --message "Execute ATP T3 worker: cleanse atp-instance/reports/, validate any open PRs in ATP repo, synthesize cross-run anomaly patterns. Per atp/lib/workers/tiers/t3.md." \
  --announce \
  --channel <ops-channel> \
  --to <ops-channel-id>
```

## PR Event Trigger (template)

```json
{
  "message": "Execute ATP T3 PR validation for PR #<number>. Deep validate all changed files, run verify_cmd where applicable, check cross-PR patterns, provide structured review comment. Per atp/lib/workers/tiers/t3.md.",
  "model": "capable",
  "name": "atp-t3-pr-<pr-number>"
}
```

## What T3 Does NOT Do
- Open new PRs (reviews existing PRs only)
- Run bulk scans across unchanged files (that's T1)
- React to push events (that's T2)
- Bypass the human merge gate — T3 approves, humans merge
- Emit unsanitized training pairs — the privacy scrubber is a hard gate, not a best-effort filter
- Delete, archive, or mutate the `atp-instance/corrections/` corpus during cleanse — the corpus is append-only by design
- Train a model itself — it captures pairs only; fine-tuning is a separate out-of-band workflow
