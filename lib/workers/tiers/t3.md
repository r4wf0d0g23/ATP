# Worker Tier 3 — Deep Validator

## Identity
- **Competency:** Deep validation, PR quality review, report cleansing, cross-run synthesis
- **Trigger:** PR opened or updated in ATP repo; also scheduled for report cleansing
- **Model class:** `capable` (highest reasoning quality — cost decreases over time)
- **Session type:** Persistent named session (`session:atp-t3-validator`)
- **Authorization:** Read all, comment on PRs, approve PRs, cleanse reports, update var metadata

## Responsibility

T3 is the quality gate. It reasons deeply about PRs before they merge, runs actual `verify_cmd` validation, and cleanses the reports directory into a coherent, deduplicated, actionable audit trail.

## Cost-Frequency Scaling

T3 runs at a frequency governed by the `cost_efficiency_ratio` variable:

```
T3_schedule = base_schedule × (1 / cost_efficiency_ratio)
```

| cost_efficiency_ratio | Base schedule | Effective schedule |
|---|---|---|
| 1.0 | Weekly | Weekly |
| 0.5 | Weekly | 2× weekly |
| 0.25 | Weekly | 4× weekly (near-daily) |
| 0.1 | Weekly | Daily |
| 0.05 | Weekly | 2× daily |

The `cost_efficiency_ratio` is read from `atp-instance/vars/worker-config.md` at job creation time. The cron schedule is recalculated when this var is updated.

## Execution Sequence

### PR Validation Mode (triggered by PR event)

```
1. LOAD PR CONTEXT
   Read PR: title, description, diff, changed files, T1/T2 findings (from PR comments).
   Load session history: has T3 seen similar patterns in past PRs?

2. DEEP SCHEMA VALIDATION
   For each changed file in the PR:
   a. Full schema conformance check (not just required fields — validate value quality)
   b. semantic_summary quality check: is it distinctive? does it add embedding density?
      Would it retrieve correctly vs. similar protocols? If weak → request changes.
   c. preload_size_class accuracy: does the estimate match the declared requires?
   d. guardrails completeness: are there obvious failure modes not covered?
   e. escalation coverage: does every critical path have an escalation rule?

3. VERIFY_CMD VALIDATION (for var file PRs)
   Run each modified var's verify_cmd (if safe to execute in current context).
   Apply the declared validator type.
   Record validation-result.
   If pass → note in PR comment.
   If fail → block PR with explanation.

4. CROSS-PR PATTERN DETECTION
   Using persistent session history:
   Has this type of finding appeared in multiple PRs?
   If yes → surface pattern to deployment owner as a systemic issue,
   not just a one-off finding.

5. PR DECISION
   a. APPROVE: all checks pass, quality is sufficient for merge
   b. REQUEST CHANGES: specific issues found, detailed feedback provided
   c. BLOCK (critical): critical finding — escalate before any merge

6. WRITE PR COMMENT
   Structured comment format:
   - T3 Validation Summary (pass/changes-requested/blocked)
   - Findings list (if any)
   - Verify_cmd results (if applicable)
   - Pattern notes (if cross-PR pattern detected)
   - Approval signal (if clean)
```

### Report Cleanse Mode (scheduled)

```
1. LOAD ALL REPORTS
   Read all files in atp-instance/reports/.
   Parse each as worker-report.

2. DEDUPLICATION
   Find reports with identical findings (same file, same type, same description).
   Keep the most recent; remove older duplicates.
   Record dedup count.

3. STALE REMOVAL
   Reports older than 90 days with status=clean → archive to atp-instance/reports/archive/
   Reports older than 180 days → delete.
   Reports with all findings resolved → mark as resolved, archive.

4. ANOMALY SYNTHESIS
   Identify recurring finding types across reports.
   If same finding appears in ≥3 reports over ≥2 weeks → synthesize into a
   systemic-anomaly record (new finding type: cross-report pattern).
   This surfaces patterns that individual T1/T2 runs see in isolation.

5. WRITE CLEANSE REPORT
   atp-instance/reports/YYYY-MM-DD-t3-cleanse.json
   Include: duplicates_removed, stale_removed, anomalies_synthesized, patterns_detected

6. ANNOUNCE
   Send cleanse summary to ops-console.
```

## Cron Configuration (template — frequency governed by cost_efficiency_ratio)

```bash
# Base schedule: weekly. Recalculate when cost_efficiency_ratio changes.
openclaw cron add \
  --name "atp-t3-validator" \
  --cron "0 3 * * 0" \
  --tz "UTC" \
  --session session:atp-t3-validator \
  --model capable \
  --message "Execute ATP T3 worker: cleanse atp-instance/reports/, validate any open PRs in ATP repo, synthesize cross-run anomaly patterns. Per atp/lib/workers/tiers/t3.md." \
  --announce \
  --channel <ops-channel> \
  --to <ops-channel-id>
```

## PR Event Trigger (template)

```json
{
  "message": "Execute ATP T3 PR validation for PR #<number>. Deep validate all changed files, run verify_cmd where applicable, check cross-PR patterns, provide structured review comment. Per atp/lib/workers/tiers/t3.md.",
  "model": "capable",
  "name": "atp-t3-pr-<pr-number>"
}
```

## What T3 Does NOT Do
- Open new PRs (reviews existing PRs only)
- Run bulk scans across unchanged files (that's T1)
- React to push events (that's T2)
- Bypass the human merge gate — T3 approves, humans merge
